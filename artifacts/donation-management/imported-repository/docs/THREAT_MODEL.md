# THREAT_MODEL.md — Donation Management System

"Security must be included from the beginning" — this table drives implementation, not a post-hoc review.

| THREAT | MODULE-SPECIFIC ATTACK SCENARIO | IMPACT | MITIGATION REQUIRED | TEST |
|---|---|---|---|---|
| **Cross-tenant access / IDOR** | A Fundraising Staff user at Non-Profit B guesses or reuses a donor/pledge/donation UUID belonging to Non-Profit A and requests `GET /api/donations/:id` | High — exposes another org's donor PII and financial records | Every query filtered by `organization_id` from the JWT at the data-access layer, not per-handler; cross-org lookups return `404` | Create a donation in Org A; request it as an authenticated Org B user; confirm `404`, not `200` or `403` (403 would confirm existence) |
| **Broken authorization** | A Fundraising Staff user (no `donation.confirm`) directly calls `POST /api/donations/:id/confirm` | High — bypasses the finance segregation-of-duties control, finalizes a gift and issues a receipt without finance review | `requirePermission('donation.confirm')` middleware on the route, checked before the handler runs | Call the endpoint as Fundraising Staff; confirm `403`; confirm donation status is unchanged after the attempt |
| **Mass assignment / over-posting** | A client includes `"organization_id": "<other-org-uuid>"`, `"status": "confirmed"`, or `"amount_fulfilled": 999999` in a `POST /api/donations` or `PATCH /api/pledges/:id` body | High — could forge a confirmed donation, fabricate pledge fulfillment, or attempt tenant reassignment | Strict request schemas (allow-list, not deny-list) per endpoint; server-stamped fields stripped before validation, never merged from client input | Submit a create/update request with protected fields set to malicious values; confirm the stored record ignores them (e.g. donation is still `pending`, pledge `amount_fulfilled` unchanged) |
| **SQL / output injection** | A donor's `display_name` or a pledge's `notes` field contains a SQL fragment or a `<script>` payload, later rendered in a donor list or exported report | Medium–High — data corruption/exfiltration (SQL) or stored XSS against staff users (output) | Parameterized queries / ORM only, no string-concatenated SQL; output encoding on every rendered field, especially free-text fields like `notes` and `payment_reference` | Submit `'; DROP TABLE donations;--` as a donor name and `<script>alert(1)</script>` as pledge notes; confirm data is stored literally and rendered safely, not executed |
| **Invalid or malicious input** | Negative or absurdly large `amount` on a donation (`-500`, `1e18`), malformed dates, or an unsupported `payment_channel` value | Medium — corrupts financial totals and dashboard KPIs | Server-side validation on every numeric/enum/date field regardless of client-side validation; reject with `422` | Submit `amount: -100` and `amount: "abc"`; confirm both are rejected with `422`, not silently coerced to `0` or accepted |
| **Personal-data exposure (donor PII)** | A user with only `donation.view` (no `donor.view`) pulls donor email/phone/address indirectly through a donation list response that embeds full donor objects | Medium–High — PII leak beyond intended access scope | Response payloads for donation/pledge lists include only a minimal donor reference (`id`, `display_name`) unless the caller also holds `donor.view`; full donor object requires calling `/api/donors/:id` directly | Call `GET /api/donations` as a role with `donation.view` but not `donor.view`; confirm the embedded donor object excludes email/phone/address |
| **Payment/amount manipulation** | A user edits a donation's `amount` after it has been confirmed, to hide skimming or inflate a tax receipt | High — financial fraud, incorrect tax documentation | No `PATCH` endpoint exists for donation `amount` at all, at any status; correcting an error requires `refund` + new `donation.create`, both independently permissioned and logged | Attempt `PATCH /api/donations/:id` with an `amount` field; confirm the route either doesn't exist or the field is rejected/ignored; confirm no code path mutates `amount` post-creation |
| **Duplicate donations (double-submit)** | A staff user double-clicks "Record Donation" or retries a timed-out request, creating two identical donation records for one gift | Medium — inflates campaign totals and donor giving history | Idempotency key on `POST /api/donations` (client-generated request ID, server deduplicates within a time window); UI-level submit-guard as defense in depth | Submit the same donation payload with the same idempotency key twice within the window; confirm only one record is created |
| **Race condition on pledge fulfillment** | Two donations against the same pledge are confirmed concurrently, each reading a stale `amount_fulfilled` before writing, causing lost updates or over-fulfillment | Medium — incorrect pledge status, inaccurate reporting | Pledge fulfillment recalculation happens inside a database transaction with row-level locking (`SELECT ... FOR UPDATE`) on the pledge row during `donation.confirm` | Fire two concurrent `confirm` requests against donations linked to the same pledge; confirm the final `amount_fulfilled` reflects both donations, not just one |
| **Unauthorized status/state changes** | A user attempts to move a donation directly from `pending` to `refunded` (skipping `confirmed`), or reopen a `void` donation | Medium — bypasses the intended financial lifecycle and its checks | State machine enforced server-side (see WORKFLOW.md) — every transition endpoint checks current status before allowing the change, rejects with `409` otherwise | Attempt `POST /api/donations/:id/refund` on a `pending` (never confirmed) donation; confirm `409`, not `200` |
| **Cross-donor pledge linkage (subtle IDOR)** | A user submits a valid `pledge_id` belonging to Donor X while setting `donor_id` to Donor Y in the same `POST /api/donations` request | Medium–High — misattributes a gift, corrupts pledge fulfillment tracking for the wrong donor | Backend validates `pledge.donor_id === donation.donor_id` and same `organization_id` before accepting the link; mismatch returns `404` | Create Donor X with a pledge; submit a donation with Donor Y's `donor_id` and Donor X's `pledge_id`; confirm rejection |
| **Receipt fraud (unauthorized issuance/reuse)** | A user tries to trigger receipt issuance for a `pending` (unconfirmed) donation, or re-trigger issuance for an already-confirmed one to get a duplicate receipt number | Medium–High — donor could receive a tax receipt for an unfulfilled gift, or duplicate receipts enable fraudulent tax claims | Receipt creation is only reachable as an internal side effect of `donation.confirm` guarded by the `pending → confirmed` transition check; unique constraint on `(organization_id, donation_id)` in `receipts` prevents a second receipt for the same donation | Attempt to confirm an already-confirmed donation twice; confirm the second attempt returns `409` and no second receipt row is created |
| **Notification/receipt-email abuse** | A user repeatedly triggers donor-facing emails (receipt resend, acknowledgement) at high frequency, effectively spamming a donor's inbox | Low–Medium — reputational harm to the non-profit, potential abuse vector | Rate-limit resend/notification actions per donation/donor (e.g. max N resends per hour), all resend actions permissioned and logged with `issued_by` | Trigger a receipt resend action beyond the configured rate limit; confirm subsequent attempts are rejected (`429`) rather than silently sent |

## Threats Considered Out of Scope for v1 (documented, not ignored)
- **Payment gateway compromise** — not applicable in v1 since no live gateway integration exists (per SCOPING.md exclusions); revisit when payment processing is added.
- **In-kind donation valuation fraud** — deferred with the in-kind valuation feature itself.

## Design Decision to Flag in Defense
Donations have **no amount-editing path after creation at any status** — the only way to correct a wrong amount is `refund` (permissioned, logged) plus a fresh `donation.create`. This trades convenience (a simple typo requires two actions instead of one edit) for an audit trail that can't be quietly rewritten — worth defending as a deliberate financial-integrity choice, not an oversight.
